# 调试与性能分析

> "最有效的调试工具仍然是仔细思考加上恰到好处的打印语句。"
> — Brian Kernighan

## 打印调试

打印调试是指在代码中插入 `print` 语句，输出有助于理解程序实际行为与预期行为差异的信息。虽然常被嘲笑为简陋，但对于很多场景来说它效果极佳。

**最大局限**：每次程序运行时都要从头开始，必须反复缩小问题来源的范围。

## 日志记录

日志记录是打印语句的一种更有原则的用法——这些语句是长期存在的，会在代码中保留一段时间。日志服务于各种调试目的：出问题时的分析、性能分析、或功能实现。

### 非结构化日志 vs 结构化日志

- **非结构化日志**：纯文本描述程序正在做什么
- **结构化日志**：指标、JSON对象等——便于后续提取和解析的数据。结构化日志让你使用 shell 工具提取信息变得简单得多。

### 日志级别

大多数日志系统使用严重级别：

| 级别 | 用途 |
|------|------|
| `TRACE` | 最细粒度的细节 |
| `DEBUG` | 调试信息 |
| `INFO` | 一般信息性消息 |
| `WARN` | 警告情况 |
| `ERROR` | 错误情况 |
| `CRITICAL` | 致命错误 |

在生产环境中，你通常只启用 `INFO` 或 `WARN` 及以上，以避免刷屏输出。调试时，你会启用更详细的日志。复杂的框架允许按模块/文件配置日志级别。

**最佳实践**：完成打印调试后，将这些 print 语句转换为正确的日志语句，这样下次程序正常运行时，你无需修改-编译循环就能获得更多信息。

### 访问第三方日志

- **命令行工具**：传入 `-v` 或 `--verbose` 获取更多输出；可以堆叠标志（`-vv`, `-vvv`）以增加详细程度
- **系统服务（Linux）**：使用 `journalctl` 检查后台服务的日志（例如 `journalctl -u sshd`）

## 调试器（GDB / LLDB）

当打印调试变得不够用——重新编译循环变得烦人，或者你不知道具体要记录什么——是时候使用调试器了。

GDB 和 LLDB 是通用调试器，接口非常相似。它们附加到正在运行的进程，允许你：

- 在特定行 / 断点处停止
- 程序暂停时检查内存
- 恢复执行直到满足条件
- 逐行单步执行代码

它们最适合编译型原生程序（C、C++、Rust）。对于解释型语言（Python、Java），使用语言特定的调试器（例如 Python 的 `pdb`）。

### 基本 GDB/LLDB 命令

- `run`（或 `r`）：从头开始启动程序
- `continue`（或 `c`）：恢复执行直到下一个断点
- `next`（或 `n`）：执行下一行（步过）
- `break <行号>`（或 `b`）：设置断点
- `print <表达式>`（或 `p`）：求值并打印表达式 / 变量
- `list`：显示源代码
- `backtrace`（或 `bt`）：显示调用栈
- `watch <表达式>`：每当表达式值改变时中断

工作流程示例：

```bash
gdb ./program
(gdb) break 52        # 在第52行设置断点
(gdb) run             # 启动程序
(gdb) print accounts[0].id
(gdb) watch accounts[0].id
(gdb) continue        # 继续向前
(gdb) reverse-continue # 向后走（配合 RR）
```

注意：断点和监视点在整个会话中的 `run` 调用之间持久保持。如果你修改了代码，必须退出并重新进入调试器。

## 反向调试（RR — 记录回放）

标准调试只能沿时间向前移动。当你发现 bug 时，你只能从那个点向前——但真正的 bug 可能 earlier 发生了。

**RR（Mozilla 的 Record Replay）** 解决了这个问题：

- 记录程序的所有操作——与操作系统的所有交互、内存访问等
- 程序从开始到结束正常执行
- 然后你可以**按倒序回放**执行过程
- 命令与 GDB 相同；区别只在于 RR 记录执行过程

**使用 RR，你可以**：

- `reverse-continue`：撤销执行直到命中监视点
- 向后单步代码找到变量确切改变的时刻
- 在 bug 发生的时刻检查调用栈

### RR 的局限性

- 需要硬件支持；**不适用于虚拟机**
- 仅限 Linux
- 如果重新编译二进制文件，必须重新录制
- "海森堡 Bug"（以不确定性原理命名）：观察时消失的 bug。RR 使用确定性调度器，这可能改变线程时序——在正常执行中出现的 bug 可能不会出现在录制中。

### RR 的使用场景

- 非确定性失败的 flaky 测试
- 难以重现的崩溃（结合 shell 讲座的 flaky 测试模式：在 RR 录制下运行测试直到失败，然后回放并调试）

## 追踪现有进程

有时你想在不修改代码的情况下理解正在运行的程序在做什么。

### strace — 系统调用追踪

`strace` 追踪进程的系统调用（内核交互）：

```bash
# 追踪你启动的程序
strace -o output.txt ls -l /tmp

# 附加到已运行的进程
strace -p <PID>

# 跟随 fork（同样追踪子进程）
strace -f ls -l

# 按操作类型过滤
strace -e trace=file ls -l      # 仅文件操作
strace -e trace=read ls -l      # 仅读调用
strace -e trace=%file ls -l     # 任何文件相关的系统调用
```

系统调用包括：`open`、`read`、`write`、`execve`、`stat`、网络操作、进程控制等。

**关于命名空间的说明**：某些系统（如 NixOS）使用命名空间隔离。在这种情况下，`ls` 本身是一个命名空间包装器，会生成真实的 `ls`。使用 `-f` 跟随 fork 并追踪所有子进程。

### BPF（扩展伯克利数据包过滤器）

`strace` 只追踪系统调用的参数和返回值——无法测量调用进入/退出之间的时序或延迟。

**eBPF** 解决了这个问题。eBPF 程序在 Linux 内核中以内核权限运行，可以检查内部内核状态。你编写类似 C 的程序在内核级别执行。

**bpftrace** 是建立在 eBPF 之上的高级工具：

```bash
# 统计所有系统调用调用次数
bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[probe] = count(); }'

# 打印每个被任何程序打开的文件
bpftrace -e 'tracepoint:syscalls:sys_enter_openat {
    printf("%s: %s\n", comm, str(args->filename));
}'

# 仅追踪特定程序（使用 $1 = 进程 ID）
bpftrace -e 'tracepoint:syscalls:sys_enter_openat / pid == $1 / {
    printf("%s: %s\n", comm, str(args->filename));
}' -c "ls -l"

# 按程序名过滤
bpftrace -e 'tracepoint:syscalls:sys_enter_openat / comm == "tmux" / {
    printf("%s opened %s\n", comm, str(args->filename));
}'
```

使用 eBPF 的内置工具：

- **biolatency**：测量磁盘 I/O 延迟分布
- **opensnoop**：记录整个系统中每个文件打开操作

### tcpdump — 网络流量分析

```bash
# 在 Wi-Fi 接口上捕获目标为 80 端口的数据包
sudo tcpdump -i wlp2s0 'tcp port 80'

# 在任何接口上捕获
sudo tcpdump -i any 'tcp port 80'
```

输出显示：源/目标 IP、端口、TCP 标志、窗口大小、数据包长度等。

- **Wireshark**：带有协议解析器的 GUI 应用（MySQL 插件、HTTP 解析器等）用于可视化数据包内容
- **MITM Proxy**：解密 HTTPS 流量以调试加密协议

## 动态分析工具（Sanitizers）

动态分析工具是编译器扩展，注入额外指令以在运行时检测 bug。

### 地址消毒剂（ASan）

检测内存错误：缓冲区溢出、释放后使用、野指针、双重释放。

```bash
# 用地址消毒剂编译
gcc -fsanitize=address -g heap_overflow.c -o heap_overflow

./heap_overflow
# 输出：AddressSanitizer: heap-buffer-overflow
# 包含：栈追踪、分配信息、内存内容
```

**没有动态分析工具时**，像堆溢出这样的 bug 可能静默破坏不相关的内存而不崩溃——使 bug 不可见。

### 其他动态分析工具

- **线程动态分析工具（TSan）**：检测线程间的数据竞争
- **未定义行为动态分析工具（UBSan）**：捕获未定义行为（空指针解引用、有符号溢出等）
- **内存动态分析工具（MSan）**：检测未初始化内存的使用

**要求**：必须使用相应的 `-fsanitize=` 标志重新编译。

## Valgrind

在你无法重新编译或需要更深入分析的情况下，**Valgrind** 是一个逐条解释程序指令的框架（它假装是 CPU）。这意味着：

- 无需插桩即可检查每个内存操作
- 精确的分析（准确的指令和周期计数）
- 检测动态分析工具会遗漏的 bug

**缺点**：极其慢（比正常执行慢 10–50 倍），因为它在软件模拟器而非真实硬件上执行每条指令。

Valgrind 工具：
- **Memcheck**：内存错误检测器（类似于 ASan 但无需重新编译）
- **Cachegrind**：缓存和分支预测分析器
- **Callgrind**：详细的调用图分析

## AI 辅助调试

大语言模型特别适用于：

1. **神秘错误消息**：它们可以解释出了什么问题并建议变通方案
2. **跨语言边界 bug**：Python 程序调用 Rust 库调用 C 库——LLM 可以追踪所有三层，在每层重现 bug，并确定根本原因
3. **导航深层栈追踪**：10+ 层深的栈追踪可能很乏味；LLM 可以识别相关栈帧

**局限性**：不擅长自动修复 bug，但非常擅长发现它们。

## 性能分析

性能分析与调试密切相关——理解代码做什么也能揭示它的性能如何。

### 计时工具

**内置 `time` 命令**：

```bash
time curl http://example.com
```

输出：
- **real**：墙上时钟时间（从开始到结束）
- **user**：执行代码所花费的 CPU 时间
- **sys**（或 **kernel**）：内核中花费的 CPU 时间（系统调用）

示例：
```
real    0m0.130s
user    0m0.054s
sys     0m0.009s
```

墙上时钟时间和 CPU 时间的差异 = 等待所花费的时间（I/O、网络等）。

**hyperfine**：统计基准测试工具，多次运行命令并提供标准差：

```bash
hyperfine --prepare 'sync; echo 3 > /proc/sys/vm/drop_caches' \
    'find . -type f' 'fd .'
# 输出：find 比 fd 快 40.15 倍
```

### 系统资源监控

**htop**：显示每核 CPU 利用率、内存使用、负载平均值、每进程统计（I/O、网络等）。

- 负载平均值：不同时间窗口（1 分钟、5 分钟、15 分钟）有多少 CPU 核心被需求
- 可按不同列排序
- 标签页：CPU、内存、I/O、网络

**专业工具**：
- **iotop**：每个进程的详细磁盘 I/O
- **free**：内存使用
- **lsof**：每个进程打开的文件
- **ss**：网络连接（开放端口、连接）
- **nethogs**：每个进程的网络使用
- **btop**（更好的 htop）：带有详细磁盘/网络统计的综合系统监控

### 使用 perf 进行程序性能分析

`perf` 是一个采样分析器——它周期性暂停程序并记录每个 CPU 正在执行的位置。

```bash
# 用调试符号编译
gcc -g slow.c -o slow

# 运行程序时记录分析数据
perf record -g ./slow

# 生成报告
perf report
```

输出显示：
- **children %**：此函数及其后代中的时间
- **self %**：仅在此函数中花费的时间

你可以：
- 展开函数查看时间花在哪里（例如 `cosine` 和 `sin` 各消耗约 43%）
- 注解源代码：查看与源代码行交织的原始汇编，显示哪些指令消耗了最多时间

### 火焰图

人类解析大规模 `perf report` 数据很困难。**FlameGraph** 将其可视化：

```bash
perf script | stackcollapse-perf.pl | flamegraph.pl > output.svg
```

生成的 SVG：
- X 轴：时间（火焰的跨度）
- Y 轴：调用栈深度
- **宽度** = 花时间比例
- **可点击**：放大特定帧

每种颜色代表不同类别（系统调用、用户函数等）——宽火焰表示热点。

### 可视化与绘图

**快速终端绘图**：`gnuplot`

```bash
echo "plot '-' with lines" | gnuplot -e "set terminal dumb; plot '-'"
```

**更深入分析**：Python 的 `matplotlib` 或 R 的 `ggplot2`

`ggplot2` 的**分面包装**对于性能分析特别强大：你可以将多维数据（例如程序运行时长 vs. 输入大小，在不同模式复杂度下）可视化为图表网格，使模式和扩展悬崖在视觉上显而易见。

## 关键原则：早日志、结构化日志

思考日志记录的最佳时机是编写代码的时候。如果你预见到以后需要什么信息（输入大小、函数时序、内部状态如图大小），你就会有现成的结构化数据用于：

- 出问题时调试
- 绘制性能曲线
- 识别扩展悬崖

结构化日志（指标、JSON）使这些数据易于解析和可视化。

---

**按用例分类的工具总结**：

| 问题 | 工具 |
|------|------|
| 快速 bug 追踪 | `print` / 日志记录 |
| 单步调试代码 | GDB / LLDB |
| 找到值改变的位置 | RR（反向调试） |
| 追踪系统调用 | `strace` |
| 内核级追踪/计时 | eBPF / `bpftrace` |
| 网络调试 | `tcpdump`，Wireshark |
| 内存错误（已编译） | 地址消毒剂 |
| 内存错误（无需重新编译） | Valgrind（Memcheck） |
| 性能瓶颈 | `perf` + 火焰图 |
| 统计基准测试 | `hyperfine` |
| 系统资源使用 | `htop`，`btop` |
