## 1. 代码格式化工具

### 1.1 什么是代码格式化工具

**代码自动格式化器（Code Auto Formatters）** 能够自动美化代码的表面语法。使用这些工具的好处是：
- 让工具自动化处理编写代码时繁琐的细节工作
- 使代码保持整洁美观
- 将精力集中在更深层次、更有挑战性的问题上

### 1.2 常见格式问题

视频演示的案例代码中存在以下格式不一致问题：

| 问题类型 | 示例 |
|---------|------|
| 引号风格不统一 | 有时用 `"双引号"`，有时用 `'单引号'` |
| 运算符空格不一致 | `a+b` vs `a + b` |
| 函数定义间距不一致 | 多余或缺失的空行 |
| 不必要的换行位置 | 在不恰当的位置换行 |

### 1.3 格式化工具的使用方式

格式化工具通常提供两种模式：

1. **检查模式（Check Mode）**：仅检查代码是否符合格式标准
2. **修复模式（Fix Mode）**：自动修复不符合标准的问题

**演示命令：**

```bash
# 检查格式是否符合标准
hatch fmt -f --check

# 自动修复格式问题
hatch fmt -f
```

> **注意**：视频中使用 `Hatch` 作为 Python 项目管理器。Hatch 内置了 `ruff` 格式化器作为默认 formatter。

### 1.4 配置选项

不同的格式化工具在配置灵活性上有差异：

| 工具类型 | 特点 |
|---------|------|
| 高可配置性工具 | 可以自定义引号风格、空格规则等 |
| 低可配置性工具 | 强制统一标准，减少团队在格式上的争论（bike shedding） |

### 1.5 EditorConfig

**EditorConfig** 是一个配置文件格式和 IDE 插件类，用于帮助不同编辑器/IDE之间保持一致的编码标准。

**典型配置示例**（`.editorconfig` 文件）：

```ini
root = true

[*]
end_of_line = lf
insert_final_newline = true
charset = utf-8
trim_trailing_whitespace = true

[*.py]
indent_style = space
indent_size = 4
```

**解决的问题**：
- 不同开发者使用 VIM、VS Code、CLion 等不同编辑器
- 避免缩进级别不匹配（如有人用 4 空格，有人用 Tab）
- 统一换行符（LF vs CRLF）
- 自动删除行尾空格

## 2. 代码检查工具（Linters）

### 2.1 什么是 Linter

**Linter** 运行**静态分析**来检查代码，不需要实际运行程序。它比格式化工具深入一层，进行**语义层面**的分析，目的是：
- 发现代码中的反模式（anti-patterns）
- 检测潜在问题
- 在这些小问题变成实际运行的 bug 之前就捕捉到

### 2.2 Linter 的一般特性

| 特性 | 说明 |
|-----|------|
| 静态语义分析 | 不执行代码，分析代码结构 |
| 内置规则列表 | 大多数 linter 提供预设规则，可按项目配置 |
| 支持禁用规则 | 可按文件或按行禁用特定规则 |
| 自动修复 | 部分规则可以安全地自动修复 |
| 文档完善 | 优秀 linter 会在报错时说明：正在查找什么模式、为什么这个模式不好、建议用什么替代 |

### 2.3 Ruff Linter 演示

视频演示使用 **Ruff** 作为 Python 的 linter。

**运行命令：**

```bash
# 仅检查问题
hatch run lint --check

# 自动修复可修复的问题
hatch run lint --fix

# 包括不安全的修复
hatch run lint --unsafe-fixes
```

**Ruff 检测出的问题示例：**

| 问题 | 规则代码 | 说明 |
|------|---------|------|
| `import *` | F403 | 导致其他静态分析更困难 |
| 导入未排序 | E401 | 代码整洁性 |
| 未使用的导入 | F401 | 如 `os` 模块被导入但未使用 |
| `if...elif` 结构 | SIM108 | 前置分支已有 `return`，不需要 `elif` |

### 2.4 使用 `# noqa` 注释忽略特定行

当需要保留某行代码但暂时不想修改时（可能是设计选择），可以使用 `noqa` 注释：

```python
from minilib import *  # noqa: F403
```

格式：`# noqa: <规则代码>`

### 2.5 从 Linter 学习更好的代码实践

**示例：异常处理规则（F401）**

Linter 报错：异常信息不应直接使用字符串字面量

**错误写法：**
```python
raise RuntimeError("some value is incorrect")
```

**正确写法：**
```python
message = "some value is incorrect"
raise RuntimeError(message)
```

**原因**：当使用 `raise` 语句时，Python 会显示堆栈跟踪信息。如果在 `raise` 同一行使用字符串字面量，错误消息会在堆栈跟踪中显示两次，造成冗余。

### 2.6 自定义 Linter 规则与 SygmalcGP

**SyGMaL**（Syntactic Grep）：解析目标语言的语法树进行搜索，比纯文本正则更准确。

**场景**：内置的 linter 规则可能没有覆盖所有你想检查的模式。

**示例需求**：查找所有使用 `subprocess` 且 `shell=True` 的代码调用。

**用 `ag`（Silver Searcher）的正则方案：**
```bash
# 脆弱：代码格式稍变就无法匹配
ag 'subprocess\.check.*shell\s*=\s*True'
```

**用 SyGMaL 的方案：**
```bash
sgrep --lang py 'subprocess.check_call|check_output(...) shell=True ...'
```

即使代码跨行书写，SyGMaL 也能正确匹配。

## 3. 软件测试

### 3.1 测试的核心价值

软件测试是提高代码可信度的标准技术：
- 编写代码后，再编写测试代码来执行已编写的代码
- 评估代码是否按预期行为运行
- 测试具有长期价值：随着代码演进，持续运行测试确保没有破坏已有功能

### 3.2 测试的层次与类型

| 类型 | 说明 | 示例 |
|-----|------|------|
| 单元测试（Unit Tests） | 测试独立函数/模块 | 测试 `fizzBuzz()` 函数 |
| 集成测试（Integration Tests） | 测试不同模块间的交互 | 模块 A 与模块 B 的交互 |
| 功能测试（Functional Tests） | 端到端测试，验证用户需求 | 完整的用户操作流程 |

### 3.3 测试驱动开发（TDD）

一种开发方法：
1. 先通过测试表达对函数的规格（specification）
2. 再实现代码
3. 运行测试确认实现满足规格

### 3.4 单元测试示例

视频使用 **pytest** 框架和 **Hatch** 项目管理器。

**测试文件命名**：`test_*.py`

**测试函数示例：**
```python
# tests/test_fizzbuzz.py
from minilib import fizzBuzz

def test_fizzbuzz_of_three():
    assert fizzBuzz(3) == "Fizz"

def test_fizzbuzz_of_fifteen():
    assert fizzBuzz(15) == "FizzBuzz"
```

**运行测试：**
```bash
hatch test
```

**发现 Bug**：测试失败后，分析代码发现 `fizzBuzz` 函数中处理同时是 3 和 5 倍数的逻辑顺序有问题。

### 3.5 代码覆盖率（Code Coverage）

**代码覆盖率** 是一个指标，用于衡量测试对代码的覆盖程度。

**工具命令（使用 coverage）：**
```bash
# 运行测试并生成覆盖率报告
hatch test -c

# 生成 HTML 格式报告（便于可视化查看）
hatch run coverage html
```

**覆盖率报告示例：**
```
18 statements, 9 missed
Coverage: 50%
```

在生成的 HTML 报告中：
- 白色/无背景的代码行：已被测试覆盖
- 标记颜色的代码行：未被测试覆盖

**提高覆盖率示例：**
```python
def test_fizzbuzz_multiple_of_95():
    assert fizzBuzz(95) == "Buzz"  # 覆盖处理 5 倍数的分支
```

重新运行后，覆盖率从 50% 提升到 61%。

> **注意**：高代码覆盖率不等于高质量测试。AI 生成的测试可能达到 100% 覆盖率但实际意义不大。

### 3.6 属性测试（Property-Based Testing）

属性测试不测试具体的输入输出对，而是定义函数应满足的**数学性质**，让测试库自动生成大量随机输入来验证。

**起源**：Haskell 的 **QuickCheck** 库

**Python 实现**：**Hypothesis** 库

**FizzBuzz 的属性示例：**

```python
# tests/test_leftpad_property.py
from minilib import left_pad
from hypothesis import given, strategies as st

@given(s=st.text(max_size=20), i=st.integers(min_value=0, max_value=50))
def test_left_pad_minimum_length(s, i):
    """填充后字符串长度至少为指定长度"""
    assert len(left_pad(s, i)) >= i

@given(s=st.text(max_size=20), i=st.integers(min_value=0, max_value=50))
def test_left_pad_contains_original(s, i):
    """原始字符串应包含在填充后的结果中"""
    assert s in left_pad(s, i)
```

**Hypothesis 的作用**：
- 生成大量随机输入（文本和整数）
- 验证属性是否成立
- 如果失败，提供具体的反例（counterexample）

**反例示例：**
```
s = "is", i = 1
Property test failed: "is" not in left_pad("is", 1)
```

**局限性**：属性测试定义的是**部分规格**，而非完整数学证明。broken 实现有时也能通过部分属性测试。

## 4. 预提交钩子

### 4.1 概念

**预提交钩子（Pre-commit Hooks）** 是一种 Git 机制，可以在任何 `git commit` 发生之前运行脚本。

### 4.2 配置

使用 `pre-commit` 工具，在项目根目录创建 `.pre-commit-config.yaml`：

```yaml
repos:
  - repo: local
    hooks:
      - id: format
        name: format
        entry: hatch fmt --check
        language: system
        pass_filenames: true
        types: [python]
```

### 4.3 使用流程

```bash
# 一次性安装预提交钩子
pre-commit install

# 尝试提交代码
git commit -m "some changes"

# 如果格式检查失败，commit 会被阻止
# 直到修复所有问题后才能完成提交
```

**可跳过检查（慎用）：**
```bash
git commit --no-verify -m "emergency fix"
```

### 4.4 价值

- 强制所有团队成员在提交前通过格式检查
- 防止格式不一致的代码进入版本控制
- 即使有人忘记手动运行格式化工具，也能自动检查

## 5. 持续集成

### 5.1 概念

**持续集成（Continuous Integration, CI）** 服务（如 GitHub Actions）在远程服务器上运行软件，当仓库发生特定事件时自动触发。

### 5.2 触发条件

```yaml
on:
  push:
  pull_request:
  schedule:
    - cron: "0 9 * * 1"  # 每周一早上 9 点
```

| 触发方式 | 典型用途 |
|---------|---------|
| `push` | 代码推送时运行检查 |
| `pull_request` | PR 提交时自动测试 |
| `schedule` | 定时运行，捕获依赖破坏性变更 |

### 5.3 CI 中的代码质量检查

CI 适合运行的各种检查：
- 格式化检查
- Linter 检查
- 类型检查
- 测试套件
- 代码覆盖率（可上传到 Codecov 等服务）

### 5.4 测试矩阵

CI 的重要能力：在多个平台/版本上并行运行测试。

```yaml
strategy:
  matrix:
    python-version: ["3.7", "3.8", "3.9", "3.10", "3.11", "3.12"]
    os: [ubuntu-latest, windows-latest, macos-latest]
```

### 5.5 GitHub Actions 配置示例

项目中的 `.github/workflows/` 目录存放配置文件：

```yaml
name: CI

on:
  push:
  pull_request:

jobs:
  format:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - run: pip install hatch
      - run: hatch fmt --check

  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
      - run: pip install hatch
      - run: hatch run lint

  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.10", "3.11", "3.12"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - run: pip install hatch
      - run: hatch test
```

### 5.6 持续部署（Continuous Deployment）

基于 CI 基础设施，自动部署软件：
- 为多操作系统编译二进制文件并自动发布
- 自动部署应用到 Web 服务
- 如 Missing Semester 课程使用 GitHub Pages 自动发布更新后的网站

## 6. 命令运行器

### 6.1 概念

当项目命令较长时（如 `python -m pytest --cov=src tests/ --cov-report=html`），每次输入很繁琐。

**命令运行器（Command Runner）** 允许定义短别名来简化命令。

### 6.2 Just

**Just** 是一个命令运行器（类似 make，但更现代）。

**配置文件示例**（`justfile`）：

```justfile
# 运行类型检查
typecheck:
    mypy --strict src/

# 运行格式化
format:
    hatch fmt

# 运行所有检查
check: format typecheck test

# 运行测试
test:
    hatch test

# 运行 Linter
lint:
    hatch run lint
```

**使用方式：**
```bash
just typecheck
just format
just check  # 运行多个命令
```

> **注意**：视频中使用 Hatch 项目管理器，它本身也支持类似功能（通过 `pyproject.toml` 配置），所以 Just 在该场景下略显冗余。但如果使用的是没有此类内置功能的项目/语言，Just 非常有用。

## 7. 正则表达式（补充内容）

### 7.1 什么是正则表达式

**正则表达式（Regular Expressions, Regex）** 是一种用于表示字符串集合或字符串模式的语言。

### 7.2 常见应用场景

| 应用 | 示例 |
|-----|------|
| 命令行工具参数 | `ag`, `rg` 等搜索工具 |
| 测试过滤 | pytest 使用 `-k` 参数支持正则过滤测试名 |
| IDE 搜索 | 在编辑器中进行模式匹配搜索 |
| 搜索替换 | 带有捕获组的复杂替换 |
| 轻量级解析 | 解析日期、邮箱等固定格式 |

### 7.3 基本语法

| 语法 | 含义 | 示例 |
|-----|------|------|
| `abc` | 匹配字面量字符串 | `abc` 匹配 "abc" |
| `[abc]` | 字符类：匹配任一字符 | `[abc]` 匹配 "a", "b", 或 "c" |
| `[^abc]` | 否定字符类 | `[^abc]` 匹配非 a/b/c 的字符 |
| `[a-z]` | 字符范围 | `[a-z]` 匹配小写字母 |
| `a\|b` | 或（交替） | `hello\|world` 匹配 "hello" 或 "world" |
| `\.` | 转义特殊字符 | `\.` 匹配字面量 "." |
| `\d` | 数字字符 | `\d+` 匹配一个或多个数字 |
| `\w` | 单词字符（非数字） | `\w+` 匹配一个或多个单词字符 |
| `\b` | 单词边界 | `\bdef\b` 匹配独立的 "def" |
| `^` | 行首 | `^world` 匹配行首的 "world" |
| `$` | 行尾 | `world$` 匹配行尾的 "world" |
| `.` | 任意字符 | `a.c` 匹配 "abc", "aXc" 等 |
| `+` | 一个或多个 | `\d+` 匹配至少一个数字 |
| `*` | 零个或多个 | `\d*` 匹配零个或多个数字 |
| `(...)` | 捕获组 | `(\d+)` 捕获数字部分 |

### 7.4 捕获组与搜索替换

在替换模式中，可以使用 `\1`, `\2` 等引用捕获组：

**Vim 示例：**
```vim
# 将所有数字替换为数字的重复（如 15 → 1515）
:%s/\(\d\+\)/\1\1/g
```

### 7.5 Python 中的正则

```python
import re

# 匹配日期格式：YYYY-MM-DD
m = re.match(r'(\d{4})-(\d{2})-(\d{2})', '2026-01-23')

if m:
    year = m.group(1)      # '2026'
    month = m.group(2)     # '01'
    day = m.group(3)       # '23'
```

### 7.6 正则表达式的局限性

正则表达式**不是**万能的：
- 无法正确解析 HTML（需要真正的解析器）
- 无法处理嵌套结构
- 适合简单字符串模式匹配，不适合复杂语法分析

**适合使用正则的场景**：日期格式、固定格式日志、邮箱地址等简单模式。

## 8. Q&A 精选

### Q1: 如何用 AI 提高代码覆盖率？

**A**：可以建立闭环流程：
1. 让 AI 运行测试和覆盖率工具
2. 生成覆盖率报告（推荐 XML 格式，便于 AI 分析）
3. 让 AI 分析报告并补充测试
4. 重复直到达到目标覆盖率

**提示**：
- 代码覆盖率不是完美指标
- AI 生成的测试可能达到 100% 覆盖率但实际无用
- 需要指导 AI 测试特定功能，而不仅仅是"写测试"
- 应该审查 AI 的输出，不能完全信任

### Q2: 测试应该写在单独的测试文件还是源代码中？

**A**：取决于测试的复杂度和语言惯例：

| 情况 | 建议 |
|-----|------|
| Rust | 通常在同一个文件中编写单元测试 |
| Python | 通常放在单独的 `tests/` 目录 |
| 小型简单测试 | 可以在源代码附近 |
| 复杂的集成/功能测试 | 建议单独文件/目录 |

对于编译型语言，放在同一文件可能会导致修改测试时需要重新编译整个项目。

### Q3: 如何测试涉及 API 调用的代码？

**A**：可以使用 **Mocking** 技术：

1. **Mock**：实现 API 的相同接口，但使用自己编写的简单实现
2. **注入**：在测试时让被测代码使用 Mock 而非真实的 API 调用
3. **VCR/Recording**：首次运行时记录真实 API 交互，之后重放用于后续测试

**Mock 的优势**：
- 完全控制返回结果
- 可以模拟错误场景
- 不需要网络连接
- 测试速度更快

### Q4: 好的 AI 提示词在哪里找？

**A**：
- 各 AI 公司的官方指南（Anthropic、OpenAI 等都提供了很好的使用指南）
- YouTube 上有人录制与 AI Agent 协作编程的视频
- 技术博客和社交媒体上有人分享经验
- 提示词通常需要根据你的具体代码库定制，泛用性模板较少
