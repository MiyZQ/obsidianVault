## 1. 依赖管理基础

### 问题引入

当代码在不同机器上运行时，可能出现环境不一致的问题。代码不仅依赖于源代码本身，还隐式依赖于：

- 编程语言运行时（如 Python 解释器）
- 第三方库（requests、numpy 等）
- 操作系统特性
- 系统级依赖（C 编译器、驱动等）

### pip 依赖安装

以 Python 为例，一个简单的 HTTP 请求程序：

```python
# greet.py
import requests
response = requests.get('https://missing-semester-2024.github.io')
print(response.status_code)
```

运行时报错：
```bash
ModuleNotFoundError: No module named 'requests'
```

这是因为 `requests` 不是 Python 标准库，需要额外安装。Python 默认的包管理工具是 `pip`：

```bash
pip install requests
```

安装过程中会看到大量输出，这是因为 pip 需要：
1. 访问 Python Package Index (PyPI)
2. 解析 `requests` 的所有依赖
3. 递归下载依赖的依赖（形成依赖树）
4. 按正确顺序安装到文件系统

安装完成后，程序可以正常运行，200 是 HTTP 状态码表示成功。

```bash
> python fetch.py
Status: 200
> pip list | grep requests
requests         2.32.5
> python -c 'import requests; print(requests.__path__)'
['/home/.../python3.11/site-packages/requests']
```

### 不同语言的处理方式

| 语言/工具 | 包管理工具 | 特点 |
|---------|----------|------|
| Python | pip、uv | 规则由 PEP 规范定义，工具可自由实现 |
| Rust | Cargo | 统一工具，完成编译、打包、发布所有功能 |
| LaTeX | 预装数千包 | 大多数包已随语言分发，很少需要手动安装 |

## 2. 虚拟环境

#虚拟环境

### 依赖冲突问题

当项目增多时，可能遇到版本冲突：

```bash
# 假设安装库A要求 numpy>=2.0
pip install "numpy>=2.0"
# 库B要求 numpy<2.0
pip install "numpy<2.0"
```

这会导致无法同时满足两个库的要求，这种问题称为 **dependency hell**（依赖地狱）。

### 创建虚拟环境

使用 Python 内置工具创建隔离环境：

```bash
python -m venv my-env
```

这会创建一个完全独立的环境副本，激活后：

```bash
source my-env/bin/activate
```

- Python 可执行文件指向新创建的文件夹
- pip 指向新环境的包
- 新环境没有任何已安装的包（不含全局安装的 requests）

可以在隔离环境中独立安装：

```bash
# 在虚拟环境中安装
pip install requests
```

检查请求位置可以看到它安装在隔离环境中，而非默认位置。

### uv 工具

`uv` 是现代 Python 包管理工具，具有以下优势：

- **速度极快**：依赖解析和安装比 pip 快数倍
- **统一工具**：替代 pip、venv 等多种工具
- **跨平台**：支持 Windows、macOS、Linux

创建虚拟环境：

```bash
# 创建
uv venv my-env

# 激活
source my-env/bin/activate

# 查看已安装包
uv pip list

# 安装包
uv pip install requests
```

> [!NOTE]
> powershell 中激活：`my-env\Scripts\activate.ps1`
> cmd 中激活：`my-env\Scripts\activate.bat`

### Python 版本隔离

虚拟环境不仅隔离包，还能隔离 Python 版本：

```bash
# 当前系统可能是 Python 3.11
python --version  # Python 3.11.12

# 创建 Python 3.12 环境
uv venv my-env --python 3.12

# 激活后
python --version  # Python 3.12.4
```

## 3. 创建可安装的包

### 问题

直接在其他目录无法导入本地模块：

```bash
# 在同一目录可以工作
python -c "from greeting import hello"  # ✓

# 切换目录后失败
cd /tmp
python -c "from greeting import hello"  # ✗ ModuleNotFoundError
```

Python 默认只搜索当前目录的 `.py` 文件，无法找到未安装的包。

### pyproject.toml 配置

需要按照 Python 规范创建包定义文件。示例 `pyproject.toml`：

```toml
[project]
name = "greeting"
version = "0.1.0"
description = "A simple greeting library"
dependencies = [
    "typer>=0.9",
]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project.scripts]
greet = "greeting:cli"
```

**配置说明**：

| 字段 | 作用 |
|-----|------|
| `name` | 安装后的包名，pip 用它查找包 |
| `version` | 版本号，用于版本约束 |
| `dependencies` | 声明依赖，格式为 `包名>=最低版本` |
| `build-system` | 指定构建工具（hatchling、setuptools 等） |
| `project.scripts` | 创建命令行工具入口，`greet` 命令调用 `greeting` 包的 `cli` 函数 |

### 安装本地包

```bash
uv pip install .
```

安装后：
- 在任何目录都能导入包
- `greet` 命令全局可用

```bash
python -c "import greeting"  # ✓ 任何位置都可用
greet --name "World"        # ✓ 命令行工具可用
```

## 4. 构建与分发

### 源代码 vs 预构建产物

**源代码分发**的问题：
- 用户需要完整的构建工具链
- 需要安装所有开发依赖（C 编译器等）
- 构建过程可能耗时且容易出错

**预构建产物（artifact）** 的优势：
- 用户下载后直接运行
- 无需构建环境
- 跨平台需要提供多个预编译版本

### ripgrep 的分发模式

以 ripgrep 为例，GitHub Releases 页面提供：
- 不同操作系统的版本（Windows、macOS、Linux）
- 不同 CPU 架构（x86_64、ARM64 等）
- 用户下载对应的二进制文件即可运行

### 构建 Python wheel

wheel 是 Python 的标准化分发格式，本质是包含元数据的 zip 文件。

```bash
# 构建 wheel
uv build
```

生成两个文件：
1. 源代码分发包（`.tar.gz`）
2. wheel 包（`.whl`）

wheel 文件内容：
- 代码文件（如 `greet.py`）
- 元数据文件（包名、版本、依赖等）

### 分发 wheel

用户拿到 `.whl` 文件后可以直接安装：

```bash
pip install greeting-0.1.0-py3-none-any.whl
```

无需源代码，无需构建过程。

## 5. 语义化版本控制

### 版本号格式

语义化版本（Semantic Versioning）格式：`主版本.次版本.补丁版本`

```
15.1.0
 ↑  ↑  ↑
M  m  p
```

### 版本更新含义

| 更新类型 | 示例 | 含义 |
|---------|------|------|
| 主版本更新 | 14.x.x → 15.0.0 | 可能破坏向后兼容 |
| 次版本更新 | 15.0.x → 15.1.0 | 新增功能，保持向后兼容 |
| 补丁版本更新 | 15.1.0 → 15.1.1 | Bug 修复，不影响功能 |

### 版本约束语法

```toml
# 精确版本
"typer==0.21.1"

# 最低版本
"typer>=0.9"

# 版本范围
"numpy>=2.0,<3.0"
```

### 依赖范围的权衡

**库（libraries）** 应该使用宽松的版本约束：

```python
# requests 的依赖声明
dependencies = [
    "charset-normalizer>=2.0,<4.0",
    "idna>=2.5,<4.0",
    "urllib3>=1.21.1,<3.0.0",
]
```

原因：用户会同时安装多个库，严格约束会导致依赖冲突。

**应用程序（applications）** 应该锁定精确版本：

```python
# ripgrep 的依赖锁定
toml = "=1.82.0"
proc-macro2 = "=1.16.0"
# ... 所有依赖都精确锁定
```

原因：确保用户获得与开发者测试完全相同的环境。

## 6. 依赖锁定与可复现构建

### 锁文件的作用

仅声明版本范围不够，锁文件记录**完整的精确版本**：

```
greet/
├── pyproject.toml  → 声明 "typer>=0.9"
└── uv.lock         → 记录 "typer==0.21.1"
```

### 生成锁文件

```bash
uv lock
```

生成的 `uv.lock` 包含：
- 所有直接或间接依赖
- 每个包的精确版本
- 包的下载地址和 SHA256 校验和

### 同步锁文件

```bash
uv sync
```

根据 `uv.lock` 安装完全一致的依赖版本，确保：
- 新版本发布不会影响构建
- 团队成员获得相同环境
- CI/CD 构建结果可复现

### 跨语言对比

Rust 的 Cargo 生成的 `Cargo.lock` 格式类似：

```
[[package]]
name = "typer"
version = "0.21.1"
source = "registry+https://github.com/rust-lang/crates.io-index"
checksum = "..."
```

### 超出语言层面的依赖

有些依赖超出包管理器范围：
- GPU 驱动（CUDA）
- 数据库服务
- 系统级库

对于这类依赖，需要：
- Nix：管理整个系统的可复现环境
- 容器：打包整个运行环境

## 7. 容器化

### 虚拟机的局限性

传统虚拟机：
- 包含完整操作系统
- 开销大（GB 级别）
- 启动慢

### 容器原理

容器共享宿主机的内核和系统组件，只隔离应用层：

```
┌─────────────────────────────────────┐
│          Host Operating System       │
├─────────────────────────────────────┤
│     Container Runtime (containerd)   │
├──────────────┬───────────────────────┤
│   Container  │      Container        │
│  ┌────────┐ │   ┌────────────────┐  │
│  │ App A  │ │   │     App B      │  │
│  └────────┘ │   └────────────────┘  │
│  ┌────────┐ │   ┌────────────────┐  │
│  │  Lib   │ │   │  Lib + DB      │  │
│  └────────┘ │   └────────────────┘  │
└──────────────┴───────────────────────┘
```

优势：
- 只有 GB 甚至 MB 级别
- 启动快（秒级）
- 共享内核，几乎无性能损失

### Docker 使用

```bash
# 启动一个容器
docker run -it python:3.14 python

# 容器内交互式操作
python --version  # Python 3.14.0
exit
```

Docker Hub 提供官方镜像：
- 基于 Debian Linux
- 预装 Python 运行时
- 命名格式：`语言:版本`

### 查看容器信息

```bash
# 容器中启动bash
docker run -it python:3.14 bash

# 查看文件系统
ls

# 查看进程（容器内几乎没有系统进程）
ps

# 查看本地镜像
docker image ls
```

### 主流容器工具

| 工具 | 说明 |
|------|------|
| Docker | 最流行的容器工具 |
| containerd | Docker 使用的底层运行时 |
| Kubernetes | 容器编排平台，使用相同镜像格式 |

## 8. Docker 部署实践

### Dockerfile 语法

Dockerfile 是定义容器镜像的配置语言。

**基础 Dockerfile**：

```dockerfile
FROM python:3.14
RUN pip install uv
RUN apt-get update && apt-get install -y gcc
COPY greeting/ /app
WORKDIR /app
RUN uv pip install --system /app
```

**命令说明**：

| 指令 | 作用 |
|------|------|
| `FROM` | 基础镜像，作为起点 |
| `RUN` | 执行命令（构建时运行） |
| `COPY` | 复制文件到镜像 |
| `WORKDIR` | 设置工作目录 |

### 构建镜像

```bash
docker build -t hey docker/simple
```

docker/simple 为指定的包含 Dockerfile 的文件夹路径，镜像命名为 hey

### 运行容器

```bash
docker run hey:latest greet "from inside Docker"
```

latest 为默认标签，后面执行包和参数
### 优化 Dockerfile

**优化原则**：
1. 合并层，减少中间层
2. 清理缓存和不必要文件
3. 使用多阶段构建（可选）

**优化示例**：

```dockerfile
FROM python:3.14-slim
COPY --from=ghcr.io/astral-sh/uv:latest /uv /usr/local/bin/uv
RUN apt-get update && \
	apt-get install -y --no-install-recommends gcc && \
	rm -rf /var/lib/apt/lists/*
COPY greeting /app
WORKDIR /app
RUN uv pip install /app --system --no-cache
```

**优化点说明**：
- `python:3.14-slim` 基础镜像更小
- 合并 RUN 指令减少层数
- `--no-cache-dir` 不保留 pip 缓存，减小镜像体积
- 先复制依赖文件再复制代码，利用 Docker 层缓存

### 镜像大小对比

| 优化前 | 优化后 |
|--------|--------|
| ~2 GB | ~200 MB |

## 9. Docker Compose 多服务编排

### 问题

当应用依赖多个服务（如数据库）时：
- 需要在多个容器间通信
- 需要协调启动顺序
- 需要配置网络

### docker-compose.yml 示例

```yml
services:
  web:
    build:
      context: .
    ports:
      - "1337:1337"
    depends_on:
      - etcd
    environment:
      - ETCD_URL=http://etcd:2379

  etcd:
    image: quay.io/coreos/etcd:v3.5.9
    command: 
      - etcd
      - --listen-client-urls=http://0.0.0.0:2379
      - --advertise-client-urls=http://etcd:2379
    volumes:
      - etcd_data:/etcd-data
volumes:
  etcd_data:
```

**配置说明**：

| 配置项 | 说明 |
|--------|------|
| `services` | 定义所有服务 |
| `depends_on` | 声明启动依赖，确保先启动数据库 |
| `environment` | 传递环境变量 |
| `ports` | 端口映射 `主机:容器` |

### 使用 Docker Compose

```bash
# 启动所有服务
docker compose up -d

# 查看日志
docker compose logs -f

# 停止服务
docker compose down
```

### 服务间通信

容器间通过服务名通信（DNS 解析）：

```python
import requests

# Python 应用通过服务名访问 etcd
response = requests.put(
    "http://db:2379/v2/keys/counter",
    data={"value": new_value}
)
```

### 数据库操作示例

简单的读写操作：

```python
def get_counter():
    """获取当前计数"""
    response = requests.get(f"{ETCD_URL}/v2/keys/counter")
    return int(response.json()["node"]["value"])

def increment_counter():
    """计数器加一"""
    current = get_counter()
    requests.put(
        f"{ETCD_URL}/v2/keys/counter",
        data={"value": current + 1}
    )
```

## 10. SystemD 服务管理

### 问题

机器重启后服务不会自动启动，需要手动执行 `docker compose up`。

### SystemD 服务文件

创建服务配置文件：

```ini
[Unit]
Description=Greeting Web Service
Requires=docker.service
After=docker.service

[Service]
Type=simple
WorkingDirectory=/opt/greeting
ExecStart=/usr/bin/docker compose up
ExecStop=/usr/bin/docker compose down
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

**配置说明**：

| 配置项 | 说明 |
|--------|------|
| `Description` | 服务描述 |
| `Requires` | 依赖 docker 服务 |
| `After` | 在 docker 之后启动 |
| `ExecStart` | 启动命令 |
| `ExecStop` | 停止命令 |
| `Restart=on-failure` | 失败时自动重启 |

### 安装和启用服务

```bash
# 放置到系统目录
sudo cp greeting.service /etc/systemd/system/

# 重载 SystemD 配置
sudo systemctl daemon-reload

# 启用服务（开机自启）
sudo systemctl enable greeting

# 启动服务
sudo systemctl start greeting

# 查看状态
sudo systemctl status greeting

# 停止服务
sudo systemctl stop greeting
```

### 服务管理命令

| 命令 | 作用 |
|------|------|
| `systemctl start <name>` | 启动服务 |
| `systemctl stop <name>` | 停止服务 |
| `systemctl restart <name>` | 重启服务 |
| `systemctl status <name>` | 查看状态 |
| `systemctl enable <name>` | 开机自启 |
| `systemctl disable <name>` | 禁用开机自启 |

## 11. 发布包到仓库

### 发布到 PyPI

**使用 uv 发布**：

```bash
# 1. 确保包名唯一
# 2. 构建包
uv build

# 3. 发布到 PyPI
uv publish
```

**使用 Test PyPI 测试**：

```bash
uv publish --publish-url https://test.pypi.org/legacy/
```

发布后其他用户可以安装：

```bash
uv pip install --index-url https://test.pypi.org/simple/ missing-semester
```

### 从 GitHub 安装

pip 支持直接从 GitHub 安装：

```bash
# 安装最新代码
uv pip install git+https://github.com/user/repo.git

# 从特定 Release 安装
uv pip install git+https://github.com/user/repo.git@v1.0.0

# 从 Release 附件安装
uv pip install https://github.com/user/repo/releases/download/v1.0.0/package.whl
```

### 发布到 Docker Hub

镜像命名规则：必须以 Docker Hub 用户名为前缀。

```bash
# 构建并标记
docker build -t yourusername/greet docker/optimized

# 推送
docker push yourusername/greet:latest
```

推送后全球任何人都可以下载：

```bash
docker run yourusername/greet:latest
```

### 协作场景

团队协作时，需要：
1. 使用共同的容器仓库（Docker Hub、GitHub Container Registry）
2. 验证身份后才有权限推送私有仓库
3. 其他成员 pull 镜像即可获得完整环境

## 总结

### 依赖管理演进

```
手动下载 → pip install → 虚拟环境 → uv + 锁文件
```

### 分发形式演进

```
源代码分发 → wheel 包 → Docker 镜像
```

### 生产环境推荐做法

| 层级 | 推荐实践 |
|------|----------|
| 依赖管理 | 使用 uv 或 poetry |
| 包构建 | pyproject.toml + wheel |
| 可复现性 | uv lock 锁定所有依赖 |
| 应用部署 | Docker 容器化 |
| 服务编排 | Docker Compose |
| 进程管理 | SystemD |
| 分发平台 | PyPI / Docker Hub / GitHub Releases |

### 核心原则

1. **隔离**：每个项目使用独立虚拟环境
2. **可复现**：使用锁文件确保环境一致
3. **标准化**：遵循语言生态系统规范
4. **自动化**：用 Dockerfile 和 Docker Compose 管理部署
5. **可追溯**：记录版本变化，使用语义化版本
