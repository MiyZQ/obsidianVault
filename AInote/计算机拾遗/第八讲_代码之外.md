# 代码之外：工程师的软技能

> 本笔记基于 Missing Semester 第八讲，主题是如何成为更好的协作者

## 引言：技术之外的 50%

软件工程的成功，大约只有 50% 取决于编写好的代码和系统，另外 50% 取决于**与他人沟通协作**的能力。这些软技能包括：

- 向他人解释系统如何工作
- 从他人那里了解他们需要什么
- 与依赖你系统的工程师合作
- 参与开源生态
- 长期维护软件

工程师的沟通方式大致分为两类：**单向沟通**（写给别人看）和**双向沟通**（协作对话）。

---

## 一、单向沟通

### 1.1 代码注释

代码注释是最重要的单向沟通工具之一，但大多数注释都写错了重点。

#### ❌ 无用的注释：解释代码在做什么

```python
# 循环遍历数组
for i in range(len(array)):
    result += array[i]
```

这类注释毫无价值——代码就在那里，任何人都可以直接阅读。

#### ✅ 有效的注释：解释代码里看不出来的内容

**类型一：TODO 注释**

```python
# TODO(ali): 当支持多语言时，改用 i18n 库替代硬编码字符串
ERROR_MESSAGES = {
    "en": "File not found"
}
```

**类型二：引用外部来源**

```python
# 归并排序实现，参考：Turing, A.M. (1946). 
# "Proposed Electronic Calculator" - 原始证明了该算法的最优性
def merge_sort(arr):
    ...
```

**类型三：「为什么不」注释（Why Not）** ← 特别推荐

```python
# 注意：我们使用自定义哈希表而非标准库的 dict，
# 因为在 Python 3.7+ 中 dict 的迭代顺序与插入顺序强绑定，
# 但我们在并发场景下需要更弱的顺序保证，且标准库在
# 极端情况下有约 30% 的性能衰减（参见 Issue #4521）
custom_map = ...
```

这类注释能防止后来者重蹈覆辙。如果注释说"这里不用标准方法"，就必须解释原因。

### 1.2 README 文件

README 是项目的门面。一个好的 README 应该按以下顺序组织：

| 顺序 | 内容 | 目的 |
|------|------|------|
| 1 | 项目是什么 | 让读者理解它是做什么的 |
| 2 | 为什么值得关注 | 解释它的特别之处或优势 |
| 3 | 怎么使用 | 提供使用示例 |
| 4 | 如何安装 | 最后的最后才给安装说明 |

**常见错误**：一上来就写"先运行 `npm install`"，而读者还不知道这东西有什么用。

#### README 与 CONTRIBUTING.md 的区别

```
README.md       → 给用户看（怎么用）
CONTRIBUTING.md → 给协作者看（怎么贡献）
```

README 是面向使用者的，不应该混入开发指南、测试说明等协作相关内容。

### 1.3 Git 提交信息

提交信息应该回答的是**为什么**，而不是**是什么**——看 diff 就能知道改了什么。

#### 写好提交信息的框架

一个完整的提交信息应包含：

1. **什么迫使这个改动**（What problem forced this change）
2. **考虑过哪些替代方案**（What alternatives did you consider）
3. **改动的权衡或影响**（What tradeoffs or implications does this change have）

```markdown
feat: 优化排序算法使用归并排序替代快速排序

问题：在大数据量场景下（>100万元素），快速排序的最坏O(n²)
     情况频繁出现，导致线上出现尾延迟峰值。

考虑过的方案：
- Timsort：复杂度更低但实现复杂，引入外部依赖
- 堆排序：虽然是稳定的O(n log n)但常数因子较大

权衡：
- 牺牲约8%的平均排序性能
- 换取了可预测的O(n log n)边界和稳定的行为
- 内存占用增加约15%，但对于目标场景可接受

关联 Issue: #1234
```

#### Git Bisect 的价值完全依赖提交信息

`git bisect` 是一个强大的二分查找工具，能自动定位引入 bug 的提交：

```bash
# 告诉它正常工作的版本和有问题的版本
git bisect start
git bisect bad
git bisect good v1.0.0

# 它会自动二分查找，直到找到问题提交
# 但前提是每个提交都有清晰的 commit message
```

如果提交信息只有"fix stuff"或"update"，bisect 找到那个提交也没用。

#### 使用 `git add -p` 拆分提交

当你有一堆改动时，把它们按逻辑分成多个小提交：

```bash
git add -p
# 对每个改动块提问：
# Stage this hunk? [y/n/q/a/d/e/?]
```

典型场景：改完功能代码后顺便格式化了一下，把这两类改动拆成独立的提交更容易被 review。

### 1.4 沟通中的「克制」原则

> 读者的时间是有限的。如果文本太多，他们会选择不读。

写任何技术文档时，都应该考虑：

- 如果你是读者，会愿意读完吗？
- AI 辅助写作时尤其要注意——LLM 擅长生成大量文本，但这不意味着应该这样做
- 始终追求**简洁且完整**，而不是冗长

## 二、双向沟通：开源协作

### 2.1 提交 Bug 报告

维护者的时间极其稀缺。一个开源项目可能有数百万用户，但只有几个（甚至一个）维护者。

#### 好的 Bug 报告的组成

| 要素 | 说明 |
|------|------|
| **环境信息** | 操作系统、版本号、相关配置 |
| **期望 vs 实际** | 你以为会发生什么 vs 实际发生了什么 |
| **复现步骤** | 有编号的步骤列表，从头到尾完整 |
| **你尝试过的方法** | 展示你已经付出的努力 |

#### 最小可复现示例（Minimal Reproducible Example）

这是最有价值的贡献。步骤：

1. 从你的完整项目中剥离无关代码
2. 只保留能触发 bug 的最小部分
3. 如果是代码库，提取出只涉及该库的独立测试代码

```
❌ 无效："我的 10 万行项目编译失败"
✅ 有效："使用以下 10 行代码可以复现：..."
```

**为什么这很重要**：维护者没有时间从你的大型项目里找问题。你花时间做最小复现，是在为他们节省时间。

#### 不要发「+1」评论

```markdown
<!-- 这样的评论只是噪音 -->
+1 我也遇到同样的问题，什么时候修？

<!-- 真正有用的评论 -->
我找到了另一种复现方式：
步骤1：安装依赖 X@1.2.3
步骤2：...
这样可以 100% 复现
```

GitHub 上的 👍 表情才是正确的「+1」方式。

### 2.2 提交 Pull Request

#### PR 的基本要求

1. **每个 PR 独立可评审**——把无关的改动拆分开
2. **PR 描述中说明「为什么」项目应该接受这个改动**
3. **阅读 CONTRIBUTING.md**，遵循项目的规范

#### 关于许可证的注意事项

当你提交 PR 时，你的代码会被项目吸收，采用项目的许可证：

- 如果项目是 GPL，你的代码也将是 GPL
- 在公司工作时尤其要注意：公司可能对你贡献代码有政策限制
- 在提交前务必检查许可证

#### Fork 作为最后手段

```bash
# Fork 是复制一个仓库到你的账户下继续独立开发
# 但这意味着你要独自维护两个相似项目的更新
```

Fork 的成本很高：
- 你成为两个项目的维护者
- 原项目的改进你得手动同步过来
- 如果只是为了「我的功能没被接受」而 Fork，通常不是好理由

**真正需要 Fork 的情况**：你有一个与原项目性质完全不同的愿景，这个功能对你的项目至关重要。

#### 维护者角色的演变

成为维护者的最佳路径：

1. 持续为项目做高质量贡献
2. 证明自己是可靠、可信任的贡献者
3. 当维护者没有时间时，邀请你接手

> "你来提 PR，我负责以后维护"——这是不现实的承诺。功能会扩散到整个代码库，不存在独立维护的「50行」。

## 三、代码审查

### 3.1 审查的心态

代码审查是**异步的头脑风暴**，不是审判。

- 审查的是**代码本身**，不是写代码的人
- 目的是对话和探讨，不是挑错

### 3.2 有效的审查评论

#### ✅ 可操作的评论（Actionable）

```markdown
<!-- 不太有用 -->
不要使用全局变量。

<!-- 更好：告诉对方该怎么做，并且解释为什么 -->
建议：将这些全局变量改为 config 数据类。
好处：这样可以并行运行测试，否则多个测试会因为共享
     全局状态而互相干扰。
```

#### ✅ 用问句而非命令

```markdown
<!-- 听起来像在批评 -->
这里应该处理 null 的情况。

<!-- 协作式的询问 -->
如果传入 null 会发生什么？
```

问句让对方自己发现改进空间，协作体验更好。

#### ✅ 解释「为什么」

不只是说「别这样做」，还要说「这个项目为什么选择另一种方式」，否则对方没有上下文来理解。

### 3.3 审查的分级

区分「阻塞性」和「非阻塞性」评论：

```markdown
<!-- Nit（非阻塞）：小问题，不改也行） -->
nit: 这个变量名可以更清晰一些

<!-- Blocking（阻塞）：必须改才能合并） -->
我认为这段逻辑需要重构，否则会引入竞态条件。
```

使用这些约定可以让 PR 作者做优先级排序。

### 3.4 平衡的艺术

#### 不要留太多评论

- 评论太多 = 没人会全部看完
- 重复的模式问题只评论第一次出现的那个即可

```markdown
<!-- 不要这样 -->
第 23 行命名不规范，请用驼峰命名
第 45 行命名不规范，请用驼峰命名
第 67 行命名不规范，请用驼峰命名
...
<!-- 改为这样 -->
第一个变量处评论：项目约定使用 camelCase 命名，
请检查整个 PR 并统一修改。
```

#### 记得指出「好」的部分

如果每次开口都是「你哪里做错了」，体验会很糟糕。指出好的选择会让对方更有动力接受你的其他意见：

```markdown
这个抽象层次选得很好，兼顾了可读性和扩展性 👍
```

### 3.5 AI 审查的局限

AI/LLM 做代码审查目前有几个问题：

- **零上下文审查**：只能看到 diff 和描述，不知道项目的整体方向
- **无法判断「对项目方向是否合适」**：比如是否破坏了向后兼容性、是否与产品愿景一致
- **理解不了「破坏性变更」政策**：能复述文字但不理解实质

```markdown
# AI 审查可以：
✅ 检查代码风格
✅ 发现明显的逻辑错误
✅ 提示可能的 NullPointerException

# AI 审查做不到：
❌ 判断这个改动是否符合项目长期方向
❌ 评估对用户的影响
❌ 理解「我们还没准备好发 breaking release」
```

AI 审查是**有用的辅助工具**，但不能替代人工审查。

## 四、提问与回答

### 4.1 问出好问题的技巧

核心原则：让回答者高效地帮助你。

#### 先说明自己的理解

```
❌ "这个 API 怎么用？"
✅ "我理解这个函数是用于网络请求的，它接受 URL 和回调函数。
   但我不确定它是同步还是异步的，以及超时如何处理？"
```

#### 善用是非问句

```markdown
# 开放式问题：回答可能很长，包含你不需要的信息
"这个函数是什么行为？"

# 封闭式问题：快速定位你真正困惑的点
"这个函数是同步的还是异步的？"
```

一连串是非问句往往比开放式问题更有价值，因为它帮你精准定位理解盲区。

#### 明确承认自己的困惑

如果你试图假装理解，回答者无法知道该讲到什么程度。

#### 不要接受不完整的答案

```markdown
Q: "这段代码为什么这样工作？"
A: "因为历史原因..."
- 你点点头说谢谢然后走开 ← 这是错的
- "能具体说说是什么历史原因吗？" ← 追问直到真正理解
```

### 4.2 搜索和自助的优先性

在问人之前：

```markdown
✅ 已经用 Google 搜索过
✅ 已经查过文档
✅ 已经问过 LLM
✅ 已经仔细看过 examples/tutorial
```

这不只是为了尊重对方时间，更是因为：
- 简单问题 LLM 3 秒就能回答
- 很多问题有现成答案，不值得打断别人
- 搜索引擎找到的答案可以被后来者复用

> 这些原则同样适用于向 LLM 提问——给它足够的上下文，用是非问句追问，直到真正理解。

## 五、AI 使用礼仪

随着 LLM 在软件开发中的普及，新的软技能出现了。

### 5.1 透明度原则

**使用 AI 时必须声明**。这不是关于羞耻，而是：

- 让审阅者知道哪些代码需要额外审查
- 设置对输出质量的合理预期
- 让其他人决定是否要对该代码应用更高标准

```markdown
## PR 描述示例

这个 PR 使用 AI 生成了测试用例（80%），核心逻辑由我手动编写。
UI 层代码由 AI 生成，我已审查每一行。
数据库模型由我手动编写。

请注意：对于 AI 生成的部分，我可能没有完整的上下文理解。
```

### 5.2 团队规范

不同项目和公司对 AI 使用有不同规定：

- **法律合规**：某些数据（医疗、金融）不能离开公司网络，使用云端 LLM 可能违规
- **项目偏好**：有些项目明确规定禁止 AI 生成代码用于特定部分
- **尊重维护者**：开源项目可能有相关政策

### 5.3 学习与效率的权衡

```python
# 用 AI 写代码：效率高，学习少
# 自己写代码：效率低，学习多
```

这是一笔可以做的交易，但应该是**有意识的选择**，不是默认的逃避。

### 5.4 面试与评估场景

在考试、面试等评估场景中使用 AI：

- **没有统一答案**：不同课程、不同公司有不同规则
- **不清楚时主动询问**：宁可多问，不要默认使用然后被认定违规
- **诚实披露**：使用 AI 不是羞耻的事，但必须让对方知晓以便正确评估

## 六、关键工具速查

| 工具/命令 | 用途 |
|-----------|------|
| `git add -p` | 交互式选择改动的部分，拆分成多个提交 |
| `git bisect` | 自动二分查找引入 bug 的提交 |
| `git blame` | 查看每行代码的最后修改者和提交信息 |
| CONTRIBUTING.md | 项目贡献指南（与 README 不同） |

## 七、核心要点总结

1. **注释写给看不到代码的人**：解释「为什么」，不是「是什么」
2. **README 先说价值，再说安装**：顺序很重要
3. **提交信息是给未来的自己看的历史记录**
4. **Bug 报告要附最小复现代码**：这是在帮维护者节省时间
5. **代码审查是协作对话，不是审判**：用问句而非命令
6. **AI 使用要透明**：让审阅者知道哪些部分需要额外关注
