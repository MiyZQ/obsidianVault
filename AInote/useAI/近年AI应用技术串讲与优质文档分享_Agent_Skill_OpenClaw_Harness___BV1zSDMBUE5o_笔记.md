理解 AI 应用技术新概念之前，掌握背景至关重要。本质上工程领域的发展和模型能力提升、算法技术的发展变化是息息相关的。

**核心理念**：学海无涯，回头是岸——不是学完所有新技术，而是想清楚脉络。设身处地置身于具体时间节点：之前从业人员想做事遇到什么问题？为什么某种方案成为标准协议/行业共识/最佳实践？它解决了什么？遗留了什么问题？新东西补齐了什么？自身又有什么局限？

## 二、Transformer 架构演进（2017-2018）

### 2.1 开山之作：Attention Is All You Need（2017）

谷歌发表的这篇论文首次提出了 **Transformer 架构**，是整个大模型时代的奠基之作，至今市面上绝大多数模型仍基于此架构构建。

**Transformer 整体分为两大部分**：

| 组件 | 角色定位 | 功能描述 |
|------|----------|----------|
| 编码器（Encoder） | "只管阅读的选手" | 负责把用户输入内容转换成机器能理解的语言表示 |
| 解码器（Decoder） | "专门负责写作的选手" | 根据理解生成最终输出 |

### 2.2 GPT 的发现（2018）

OpenAI 在 GPT-1 中发现：**去掉编码器，只保留解码器，模型在创作生成任务上的表现更强**。

此后市面上的绝大多数模型沿用 **GPT 的思路，采用 Decoder-Only（仅解码器）架构**。

**三种 Transformer 变体**：

```
┌─────────────────────────────────────┐
│        Transformer 架构变体          │
├─────────────────────────────────────┤
│  1. Encoder-Decoder（完整架构）       │
│  2. Encoder-Only（仅编码器，如BERT）  │
│  3. Decoder-Only（仅解码器，如GPT）   │
└─────────────────────────────────────┘
```

## 三、提示词工程（Prompt Engineering）

大语言模型时代，人们和模型交互的基本形式是 **Chatbot（聊天机器人）**。同样一个模型、同样的对话框，为什么有人输出质量更好？这就涉及提示词工程。

**核心观点**：提示词工程不只是"语言的艺术"，真正调过 PE（Prompt Engineering）的都知道非常痛苦，涉及大量技术手段和技巧。

### 3.1 Few-Shot（少样本提示）

经典技术：在提示词中注入少量答案的标准答案示例，可以给模型输出质量带来非常好的提升，并能有效约束大模型按照期望格式输出。

### 3.2 提示词工程的局限性

- 输入窗口（上下文窗口）**有限**
- 无法将整个领域的垂类知识全部交给大模型
- 无法让模型理解训练阶段未接收的知识
- 想要提升模型某方面性能时，提示词工程能力不足

## 四、微调（Fine-tuning）

### 4.1 LoRA 论文（2021）

**必读论文**：2021 年的 LoRA 论文（[LoRA: Low-Rank Adaptation of Large Language Models](https://arxiv.org/abs/2106.09685)）

**核心贡献**：让微调这个高成本、高耗时的过程把算力成本压下来，微调开始走向千家万户，每个小团队都能调，不再是"富人的游戏"。

### 4.2 微调的实际问题

微调在工程落地中**并非任何时刻都理想的解决方案**：

| 问题 | 说明 |
|------|------|
| 成本高 | 需要训练模型，需要 GPU、需要卡 |
| 周期长 | 需要投入人力准备数据集、清洗数据、跑模型、训练 |
| 基座迭代快 | 调了几个月，新版基座大模型反手出了新版本，在你的细分领域也干掉了你 |

**典型场景**：经常出现"拿着上一个版本的基座大模型做微调，调了几个月，结果人家出了新的版本"的情况。

## 五、RAG 检索增强生成（Retrieval Augmented Generation）

### 5.1 RAG 与微调的对比

RAG 和微调解决的是**不同问题**，但有部分重叠——都可以解决"给予模型预训练阶段未接收的私有知识"的需求。

**RAG 相对微调的优势**：

- **轻量**：不需训练模型
- **成本低廉**：无需 GPU 算力
- **落地快**：实施周期短

但 RAG **没有动到模型根本能力**——没有改变任何一个参数，也没有使模型变得更聪明，所以作用有限。

### 5.2 RAG 基本原理

**三步流程**：

```
用户输入 → 向量数据库检索 → 拼接上下文 → 模型生成
  ①         ②                ③           ④
```

**生产链路**：

1. 创建知识库
2. 将自己的文档切片
3. 做向量化
4. 存入向量数据库

**消费链路（检索增强生成三步骤）**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| **①** | 用户输入提示词，请求打到服务端 | — |
| **②** | 对用户请求做 **Embedding（嵌入）**，转成向量 | 将文本转成数值向量表示 |
| **③** | 用用户请求的向量去向量数据库做**召回（Retrieve）** | 召回有相关性的文本片段 |
| **④** | 将用户输入和召回的文本片段**拼接（增强上下文）** | 组成完整的 prompt |
| **⑤** | 发给模型，模型基于所有信息**生成回复（Generate）** | 对应 "Retriever Augmented Generation" 三步骤 |

**RAG 的效果**：大幅减少幻觉现象——模型回答时可以带上真实可信的参考信息，甚至能标注"来自哪里 1234567"。

### 5.3 RAG 的工程挑战

真实工程中想把 RAG 用好是一件挺困难的事情，有非常多的门道：

- **切片**：怎么切片文档？
- **多模态数据**：文档里的多模态数据怎么入库？
- **嵌入模型**：使用什么样的 Embedding 模型？
- **检索方式**：采用怎么样的检索方式？
- **低相似度处理**：用户请求和数据库里的回答相似度低时要做什么处理？

## 六、Function Calling 与 MCP（Model Context Protocol）

### 6.1 背景问题

上面提到的技术（提示词工程、微调、RAG）都是让大模型**效果更好、回答更好**。但本质上，大模型仍然只是一个 Chatbot——只能聊天，没法帮你做更多操作。

**目标**：让模型有动手能力，能够**操作工具**。

### 6.2 Function Calling（函数调用）

**参考文档**：OpenAI 官方协议文档

**原理**：

```
用户提问
    ↓
在提示词里约束大模型返回一个规定格式的调用指令
（通常是一个 JSON 格式，包含函数名 + 参数）
    ↓
服务端解析这个 JSON
（反序列化这个调用指令，实现真正的函数调用）
    ↓
拿到结果后，发起第二轮 LM Call
（让大模型根据返回结果进行后续回答）
```

**本质**：通过工程手段巧妙实现模型调用工具——模型只负责"说"，**服务端负责"做"**。

### 6.3 MCP（Model Context Protocol）模型上下文协议

**提出方**：Anthropic（Claude 的母公司），2024 年 11 月提出

**核心问题**：Function Calling 时代，很多外部能力是可以**重复复用**的——不同团队可能都需要"查日志"这个能力，但都在重复开发。

**MCP 的解决方案**：定义一个**协议规范**，只要大家都遵循这个规范，开发出来的可供 Function Calling 的工具就能给任何适配了这个协议的 AI 应用使用。

```
┌──────────────────────────────────────────────┐
│                   MCP 协议                    │
├──────────────────────────────────────────────┤
│  工具开发者 ──→ 遵循协议开发工具 ──→ 可复用  │
│                  ↓                           │
│  AI 应用开发者 ──→ 适配协议 ──→ 可直接使用   │
│                                              │
│  → 促进生态社区繁荣                          │
└──────────────────────────────────────────────┘
```

**MCP 提出后火爆一年多**，很多公司在公司内部建立自己的 MCP Hub，实现工具复用。

## 七、Agent（智能体）

### 7.1 为什么需要 Agent

- **之前**：实现了和 AI 更好地聊天
- **之前+**：实现了 AI 操作外部工具、访问外部数据
- **但是**：AI 能像同事一样坐在旁边代替工作吗？

**答案**：暂时还不行。你甚至不能把 AI 当成一个实习生，丢一个明确的目标和所有材料给它，就期望它自己干起来。

### 7.2 Agent 的本质

一个真正的 Agent（实习生）拿到任务后会：

1. 自己理解任务目标
2. 开始想办法做**计划**
3. 结合手上的各种工具和资源**行动**
4. 在行动过程中遇到问题（环境跑不通、接口报错、不会配置等）
5. **观察**报错，分析问题
6. 回到第 2 步，继续想办法、做计划、行动

这是一个 **循环** 的过程。

### 7.3 Agent Loop（智能体循环）

**核心概念**：Agent 要模拟的就是这个 **思考 → 行动 → 观察** 的循环。

**经典论文**：**[ReAct: Synergizing Reasoning and Acting in Language Models](https://arxiv.org/abs/2210.03629)** —— 这是一切的起点，后面接触到的各种 Agent、各种设计模式、各种 Multi-Agent 架构，本质上都源于此。

**Agent Loop 流程示例**（以 AI 做排障为例）：

```
┌─────────────────────────────────────────────────────┐
│                  Agent Loop 流程                     │
├─────────────────────────────────────────────────────┤
│                                                     │
│   ① Thinking ──→ 根据目标列出计划                    │
│        ↓                                            │
│   ② Acting ──→ 根据注册的 Function Calling/MCP Tools │
│                  执行工具调用（看告警、看日志等）     │
│        ↓                                            │
│   ③ 拿到数据，再喂给大模型（Agent 主脑）             │
│        ↓                                            │
│   ④ Observing ──→ 观察数据结果                       │
│        ↓                                            │
│   ⑤ 回到 Thinking ──→ 决定下一步行动                 │
│        ↓                                            │
│   ... 循环 ...                                       │
│        ↓                                            │
│   ⑥ 认为得到最终答案 → Agent Loop 结束              │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**关键点**：

- Loop 结束节点由**大模型控制输出**
- 如果模型认为还不够，会回到循环起点继续下一步动作
- 如果模型认为已定位到问题，Loop 自动结束

### 7.4 Agent 设计模式

从 ReAct 之后，Agent 大概分出两条线：

| 方向 | 说明 |
|------|------|
| **侧重规划的 Agent** | 重点在分解任务、制定计划 |
| **侧重反思的 Agent** | 重点在执行后回顾、自我修正 |

## 八、Multi-Agent（多智能体架构）

### 8.1 为什么需要 Multi-Agent

一个 Agent 不能解决所有问题吗？原因在于前几年模型能力仍然有限：

| 问题 | 说明 |
|------|------|
| **上下文窗口有限** | 模型能处理的 token 数量有上限 |
| **注意力分散/稀释** | 给的东西太多太杂，模型会陷入混乱 |
| **工具数量限制** | 注册两三个工具可能还行，50、100 个工具时模型基本会掉准 |

### 8.2 Multi-Agent 的典型应用

设计一个自动写需求文档的 Agent 系统：

```
用户需求
    ↓
┌────────────────────────────────────────┐
│         Multi-Agent 系统               │
├────────────────────────────────────────┤
│  Sub-Agent 1：专门负责读代码           │
│  Sub-Agent 2：专门负责写代码           │
│  Sub-Agent 3：专门负责 Review 代码     │
└────────────────────────────────────────┘
```

### 8.3 Anthropic 关于 Multi-Agent 的建议

**Anthropic 发现**：Multi-Agent 架构很多时候有点泛滥了，团队投入大量时间去构建复杂的多 Agent 架构后，退回到单 Agent 架构设计 + 优化提示词 + 优化工具描述，效果反而更好。

**三种适合用 Multi-Agent 的情况**（其他情况需慎重考虑）：

| 情况 | 说明 |
|------|------|
| **① 上下文爆炸/污染** | 业务中存在上下文爆炸或上下文污染等问题，导致模型智力下降 → 需要多个子 Agent 相互隔离上下文 |
| **② 任务可并行** | 任务可以并行运行时 → 通过 Multi-Agent 提速 |
| **③ 改善工具决策/任务聚焦** | 拆分不同子 Agent 能改善工具决策效果，或让任务更加聚焦 |

### 8.4 常见的工程实现错误

**错误姿势**：按**职能工作类型**划分 Agent（一个写代码、一个测试、一个 Review）。在这种模式下，Agent 之间大量 tokens 消耗在**解释上下文、解释彼此工作**上（"拉通对齐的经历远比实际干活更费劲"）。

**正确姿势**：按**上下文隔离的边界**划分。谁掌握信息，谁就把这一块负责到底。只有当任务需要的背景信息、上下文知识完全不同的时候，才考虑拆分。

**核心原则**：**谁掌握信息，谁负责到底**。

## 九、上下文工程（Context Engineering）

### 9.1 什么是上下文工程

在 Agent 循环运行过程中，会产生越来越多的数据，这些数据可能与下一轮推理相关，包括：

- 系统提示词
- 用户的提示词
- 历史对话
- Tool 的工具描述
- 每一轮工具调用的输入输出结果
- 状态信息
- RAG 召回的数据

**上下文工程**：怎么把海量信息进行筛选和提炼，精确选取合适的信息放入下一轮模型调用的上下文窗口，以获得最好的结果。

### 9.2 为什么不能把所有信息一股脑丢进去

**问题一：上下文窗口有限**

日志返回一下就几万个 token，几个来回可能就直接把上下文窗口撑爆了。需要做压缩和裁剪。

**问题二：注意力稀释（更重要的原因）**

Transformer 基于**自注意力机制**——每一个 token 都要和输入的所有其他 token 建立关系。每多给一个 token，都在消耗模型**有限的注意力资源**。上下文越长，注意力被稀释得越严重，模型越难找到最关键的信息。

**过长的上下文可能导致的问题**（详见 LangChain 文档）：

- 冗余的上下文影响注意力
- 有毒的上下文影响决策
- 关键信息被淹没

### 9.3 上下文工程管理的四个部分

| 部分 | 说明 |
|------|------|
| **写上下文（Write Context）** | 如何组织要放入上下文的信息 |
| **选择上下文（Select Context）** | 如何筛选最相关的信息 |
| **压缩上下文（Compress Context）** | 如何对大量信息做压缩和总结 |
| **隔离上下文（Isolate Context）** | 如何通过多个 Agent 隔离不同的上下文 |

**参考资料**：LangChain 的文档对这块总结较好，建议详细阅读。

## 十、Agent Skill

### 10.1 仍然存在的问题

- **上下文爆炸问题**：每个做 Agent 的团队或多或少都遇到过
- **Agent 复用困难**：团队开发了一个归因 Agent，隔壁团队想用，需要在不同的工程架构、不同的 Agent 框架中重新接入，需要重新配置 MCP 工具、抄一遍提示词
- **非专业用户门槛高**：低代码平台（如 Coze）搭建 Agent 本质上也是在复制提示词、重新配置所有工具

### 10.2 Agent Skill 的设计亮点

**① 基于文件系统的懒加载式提示词**

传统方式：提示词在用户请求时一次性全量加载给模型

Skill 方式：

- 不同提示词以**文件系统形式**分别分类存放
- 只有需要某部分提示词时才把它拉入上下文
- 搜索过程可以理解成一种 **Agentic Search**——让 AI 直接看到文件结构，自己选择翻找哪一部分提示词

**② Agent 可复用（最重要）**

**MCP 实现了工具可复用，Skill 实现了整个 Agent 可复用**。

目标：有一个通用协议，实现：

- 团队开发了一个归因 Agent，隔壁团队可以**一键 copy**，直接拿来用
- 某个企业开源了一个很好的 Agent，不懂 AI 的人也能**低门槛使用**

### 10.3 Skill 的定义

**提出方**：Anthropic（Claude 母公司）

**官方定义**：每个 Skill 本质上就是一个**文件夹**。

**最重要的文件**：`skill.md`

其中存放了：

- Skill 的名称、描述
- 和系统提示词类似的内容
- 规定这个 Skill 能做什么
- 要怎么去执行它的脚本
- 什么时候需要阅读它的引用文件
- 什么时候需要使用它的静态资源

### 10.4 Skill 文件夹结构

```
┌─────────────────────────────────────┐
│            Skill 文件夹             │
├─────────────────────────────────────┤
│  📄 skill.md（核心配置文件）         │
│  📁 scripts/（脚本文件夹）           │
│  📁 references/（引用文件文件夹）    │
│  📁 resources/（静态资源文件夹）     │
└─────────────────────────────────────┘
```

### 10.5 Skill 的运行流程

```
下载 10 个 Skill 文件夹
    ↓
放在本地指定位置（可被 Claude Code 等本地 Coding Agent 扫描到）
    ↓
Coding Agent 启动时
    ↓
扫描指定目录
    ↓
拿到所有可用 Skill 的名称和描述
    ↓
全部塞到 Agent 主脑模型的系统提示词里
    ↓
用户发请求（如"我要实现什么功能"）
    ↓
Agent 主脑模型判断请求是否能匹配某个 Skill
    ↓
相关性强的 → 激活该 Skill
（把 skill.md 里所有内容加载到 Agent 上下文）
    ↓
任务运行过程中，Agent 发现需要看某个 reference 文件
    → 读取对应文件
    ↓
Agent 发现需要执行某个脚本
    → 启动 Sandbox 执行脚本
    ↓
拿到返回数据进一步完成任务
```

**关键理解**：在此之前（激活前），Agent 只加载了 Skill 的**名称和描述**；激活后，才会加载完整的 skill.md 内容。

### 10.6 Skill 与 MCP 的区别

| 维度 | MCP | Agent Skill |
|------|-----|-------------|
| **复用粒度** | 工具可复用 | 整个 Agent 可复用 |
| **分享方式** | 通过协议共享工具定义 | 打包成文件夹，可像发文件一样直接分享 |
| **使用门槛** | 需要工程接入 | 不懂 AI 的人也能使用 |
| **内容范围** | 工具描述、接口定义 | 系统提示词 + 脚本 + 引用文件 + 资源文件 |

## 十一、OpenClaw（小龙虾）

### 11.1 产品定位

运行在本地电脑上的**个人 AI 助手**，类似于 Siri。

### 11.2 创新点

**主要不是技术突破，而是产品创新、理念创新、交互创新**：

- 通过飞书等人类友好的入口和 Agent 交互
- 操作自己的电脑
- 帮用户实现很多私人的任务
- 对不了解 Agent 领域的人来说是新奇的体验

### 11.3 技术参考

- 可参考 OpenClaw 的**上下文管理、记忆管理**相关代码
- **注意**：OpenClaw 代码非常长，感觉都是 AI 写的

**推荐参考**：[NanoBot 项目](https://github.com/nanobot-project/nanobot)——用 1% 的代码实现了 90% 以上的功能，核心代码只有几千行，是一个 mini 版的 OpenClaw，可通过它了解基本技术原理。

## 十二、Harness Engineering（驾驭工程）

### 12.1 背景问题

即使有前面这么多技术，仍然很难实现：给 Agent 丢一个需求，让它晚上跑 8 小时代码，第二天来验收。

**原因**：不驾驭的话，AI 就像**脱缰的野马**——一觉醒来可能已经在 1000 公里以外。

### 12.2 什么是 Harness Engineering

**参考资料**：OpenAI 的文章

**核心思想**：随着 AI 变得越来越聪明，人类要做的事情不再是把需求拆得特别特别细、引用具体代码位置告诉他"123 你要怎么改"。而是要在**宏观上**去驾驭 Agent。

### 12.3 驾驭工程的四大核心要素

| 要素 | 说明 |
|------|------|
| **① 约束（Constraint）** | 限制 Agent 能做什么、边界在哪里、必须依赖什么规则、在什么范围内改动 |
| **② 上下文（Context）** | 尽可能全面地提供 Agent 完成任务所需的最完整上下文——项目迭代背景、完整需求文档、代码架构概述等。<br>**核心观点**：很多时候 AI 做错，不一定是它笨，而是不知道上下文的人也会写 bug、会踩坑 |
| **③ 验证（Verification）** | 验证 Agent 是否正确完成任务：<br>• 写完接口后让 Agent 自己写单测，要符合预期<br>• 让 AI 推代码到流水线部署，看看会不会编译报错 |
| **④ 纠偏（Correction）** | 建立科学的循环系统，在 Agent 出错时第一时间给予反馈，保障 Agent 完成自我修复，重新回到正确轨迹 |

### 12.4 实践细节

**创建 AI-Friendly（AI 友好）环境**：

- 提高代码可读性
- 避免历史遗留的"神级代码"——那种"写代码的人拉过来好好问一下"的代码，人做不到的事情不要指望 AI 能做到

### 12.5 OpenAI 的案例

OpenAI 通过**人类掌舵智能体执行**，用几周时间交付了 **100 万行代码** 的项目，代码基本由 AI 编写。

**OpenAI 的观点**：在未来，我们可能要重新定义工程师的角色，重新定义人和 AI 的工作协作交互方式。

### 12.6 工程师的应对

| 方向 | 说明 |
|------|------|
| **改变协作模式** | 学会和 AI 协作的方式，最大化发挥 Agent 潜力 |
| **AI 提效应用落地** | 建设过程也需要人力投入，会持续一段时间 |
| **新需求涌现** | 代码变得廉价后，原来不被看见的需求可能会涌现 |
| **跨行业发展** | AI 在各行各业落地稍慢一步，懂技术的人能做的事情会更多 |

## 十五、技术选型决策参考

| 场景 | 推荐方案 | 说明 |
|------|----------|------|
| 模型回答质量不够好 | 提示词工程 → 微调 | 优先提示词工程，无效再考虑微调 |
| 需要模型掌握私有知识 | 微调 vs RAG | RAG 更轻量快，但能力有限；微调更彻底但成本高周期长 |
| 模型需要调用外部工具 | Function Calling → MCP | MCP 实现工具可复用 |
| 需要模型自主完成复杂任务 | Agent / Multi-Agent | 按需使用多 Agent，注意上下文隔离边界划分 |
| Agent 上下文太长 | 上下文工程 → Multi-Agent | 优先上下文压缩/选择，无效再用多 Agent 隔离 |
| 需要复用整个 Agent | Agent Skill | MCP 解决工具复用，Skill 解决 Agent 复用 |
| Agent 需要长时间自主工作 | Harness Engineering | 约束 + 上下文 + 验证 + 纠偏 |
